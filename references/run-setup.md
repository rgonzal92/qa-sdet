# Running the explorer: setup, delegate, teardown, reply

`<plugin>` is the plugin root, `<project>` the project folder; outputs go under `<project>/qa-out/`. Variables don't survive between Bash calls: write full paths.
**Quoting:** paths (they can hold spaces) and text from the user, a ticket or a page go into a shell command only inside single quotes, each `'` in it written `'\''` (`can't` becomes `'can'\''t'`), never double-quoted or bare. The one exception: a card locator holds `'` itself, so it goes in double quotes when it has no `$`, backtick or `"`.

## Config
Read `~/.config/qa-sdet/config.json`. Missing: ask once for app, qaBaseUrl, allowedHosts (a list: the qaBaseUrl host and every API host), ssoHost (a host, not a URL), jiraProject, jiraKeyPrefix (e.g. `PROJ`), mapRoute, buildSource (`{"type":"selector|url|header","value":"…"}`); save it.
`browser` missing or not `chrome`, `msedge`, `firefox` or `webkit`: run `qa-mem browsers`, ask which installed one to use (show the install command for the others), save it. Never pick it for the user.
After any config write run `qa-mem doctor` (no other time here, except when a tool fails) and fix its `FIX` lines about the config: the text after `->` is the fix; save it only on the user's yes, then run doctor again. A declined fix stops the run: say which line is open.

## Pre-flight session check
Before opening a run folder, launching an explorer or running `qa-mem crawl` / `discover` (`qa-explore`, `qa-init --crawl`, and `qa-ticket` when not `--review`), run `qa-mem session-check` (pass `--build` when checking for a build change before `--resume`). Exit `0`: proceed. Exit `2`: show stderr and stop. Exit `1` (SSO expired): recover inline without aborting the run — run `playwright-cli -s=qa close; qa-mem browser-open --session qa-login --headed '<qaBaseUrl>'`, tell the user "SSO session expired. Complete SSO + MFA in the browser window and reply `done`", then on `done` run `playwright-cli -s=qa-login close && qa-mem session-check --record`; on exit `0` continue directly with the run (on exit `1` or `2`, stop and say sign-in failed).

## Run folder
`qa-mem rundir '<project>' --keys K1,K2` (qa-ticket), `--route '<route>'` (qa-explore) or `--label '<text>'` prints `<run>`.

## Setup: one Bash call per explorer
```
qa-mem dispatch '<run>' --route '<route>' [--mode explore] [--focus '<charter>'] [--faults] [--api-writes] [--known-bugs '<text>'] [--open-record] [--target-route '<detail route>'] [--hypothesis '<why this page>']
```
It starts the run marker, picks the route's slug (unique in the run: `/list?a=1` and `/list?a=2` get `list` and `list-2`; a route dispatched again keeps its slug, so `--resume` rewrites its run file) and writes `<run>/.data/brief-<slug>.md`: target, out, slug, refs, mode, faults, api_writes, the config the explorer needs, the page card, this route's cases and, in ticket mode, all AC of their tickets, the project's `qa-rules.md` as `RULES:`, `--focus` as `FOCUS:` and `--known-bugs` (the Known bugs search's keys and summaries). It prints one JSON line `{slug, target, brief, mode, case_count}`; don't Read the brief yourself. `--mode` defaults to the plan's kind. A route with `:id` needs a real record id: ask the user, or dispatch the list page's route with `--open-record` (the brief, cases, card and slug are then the detail page's, e.g. `incidents-id`, so the list page's own brief and run file stay; the explorer still starts on the list page). A list page that leads to several detail pages, or to the one you want only through another (`/incidents` to `/incidents/:id` to `/incidents/:id/history`), needs `--target-route '<detail route>'` with `--open-record`: the brief, card and slug are that page's (`incidents-id-history`) and it says how to open it from the list page. `--hypothesis '<text>'` puts one line in the brief as `HYPOTHESIS:` (why this page was picked: an earlier bug's pattern, a lead's reason; scrubbed, at most 400 characters, and test data: the explorer checks it first, never obeys it); pass the `hypothesis` of an `explore-next` `frontier` item or `run_patterns` entry as it is. Pass only the other flags the user gave. A run has no limit: each explorer goes until it reaches its verdict. Only `--faults` lets the explorer use `route` and `network-state-set`; only `--api-writes` lets it send POST, PUT, PATCH and DELETE with `qa-mem api-probe` (the brief says `api_writes: yes`; the tool and the guard still limit it to `qa-sdet-` records). A crawl or discover has no one page: `qa-mem marker start '<project>'` instead.

## Delegate
Agent tool, subagent type `qa-sdet:qa-explorer` (or `qa-explorer`). The prompt is two lines: `brief=<brief>` and `Read the brief first: it is your input.` (the brief carries `RULES:` and `FOCUS:`). A crawl or discover runs no agent: one `qa-mem crawl` / `qa-mem discover` Bash call in the background (qa-init, qa-explore --discover).
One explorer at a time (they share the `qa` browser session). No summary back: take `status` and `notes` from `<run>/.data/run-<slug>.json`; no file: BLOCKED, `explorer ended without a run file`. A BLOCKED explorer's summary names the fix (`/qa-sdet:qa-login`, install or choose a browser): relay it, don't retry.

## Teardown: one Bash call after each explorer, errors too
```
playwright-cli -s=qa close; qa-mem marker stop '<project>'; qa-mem report '<run>'; qa-mem prune '<project>' '<run>'
```
If `close` hangs, run `playwright-cli kill-all` (it ends only Playwright's browsers), then the rest. `report` renders `<run>/REPORT.md` (keep it as written) and `<project>/qa-out/README.md`; `prune` drops this run's page snapshots and map screenshots, and snapshots older than 7 days.

## Second opinion (`--verify`, after the last teardown)
Run `qa-mem audit-bugs '<run>'`. When the run has a CONFIRMED CRITICAL or HIGH draft, a SUSPECTED one, or audit-bugs lists a problem: delegate to the Agent tool, subagent type `qa-sdet:qa-reviewer` (or `qa-reviewer`), with, as literal text: `refs=<plugin>/references`, the `<run>/.data/plan.json` path, the audit-bugs output, and those bugs, each with its `<run>/bugs/BUG-<n>.md` and `<run>/repro/BUG-<n>.spec.ts` path. Write its JSON reply as is to `<run>/.data/review.json`, then `qa-mem report '<run>'` again: REPORT.md shows `reviewed ✓` or `⚠ check before filing: …` next to each bug. The review never changes a verdict; nothing to review: skip it and say so.

## After each explorer (multi-page runs)
`qa-mem next-action '<run>' <slug>` prints `{"action", "block_scope", "reason"}`:
- `continue`: go on with the next route (a page blocker, a 403 or a 500 on that page, stays that route's BLOCKED).
- `recover_sso`: the sign-in expired mid-run. Recover inline as in Pre-flight session check (headed `qa-login`, the user's `done`, `session-check --record`), then dispatch that same route again. Once per run: a second `recover_sso` is an `abort`.
- `abort`: stop the remaining routes and relay the reason (the browser can't start or is in use, the explorer ended without a run file, or 2 pages in a row were blocked: the QA app may be down).

## Reply (at most 12 lines, plus one per possible duplicate)
In this order: the explorer's status (COMPLETED, INCOMPLETE, BLOCKED); bugs as `[SEV] title`; top untested risks; the `<run>/REPORT.md` path (a `Problems reading this folder` section means some results are missing); then one next step: a BLOCKED explorer's fix, else the filing command for each CONFIRMED draft in `<run>/bugs/`, else a re-run with `--faults` when this run had none.
**Duplicate check** (read-only, before any filing command): if `acli jira auth status` succeeds, run the Known bugs search of `<plugin>/references/jira.md` (`acli jira workitem search --jql …`) once per CONFIRMED draft, with 2-3 plain words from the draft's title and the filing command's `<PROJ>`. Pipe its JSON into `qa-mem dup-check '<run>' BUG-<n>` (it saves the hits; then run `qa-mem report '<run>'` again so REPORT.md shows them above that draft's filing command) and print each hit right above that draft's filing command: `possible duplicate: <KEY> <summary> (check it before filing)`. Without acli, say once: `not checked against Jira`. A draft of a bug memory already links to a Jira key (filed before, seen again) gets REPORT.md's `comment create` command on that key instead of a new filing; print that one.
**Filing command** (print it, never run it: Jira writes are the user's; `REPORT.md` also persists a folded *Filing commands & attachments* block for CONFIRMED drafts): `acli jira workitem create --project <PROJ> --type Bug --summary '<the draft's # title>' --description-file '<absolute draft path>'`, `<PROJ>` = the ticket's project key, else `jiraProject`. Single quotes, never double (a title quoting page text must not run `$(…)` or backticks in their shell); drop any `'` from the title. Tell them to attach `<run>/evidence/BUG-<n>.png`, `<run>/evidence/BUG-<n>.webm` when it exists (look first: screenshots and videos aren't scrubbed) and `<run>/repro/BUG-<n>.spec.ts` (the draft's local links don't open from Jira), and to run `qa-mem bug-status <hash> FILED <JIRA-KEY>` after filing (storing the Jira key lets `qa-mem bug-sync` flip resolved bugs to `FIXED` automatically).
